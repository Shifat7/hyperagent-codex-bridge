# HyperAgent Field Report: From Agent Spend to System Controls

HyperAgent provided $5,000 in platform credits to test its model and agent infrastructure in real work.

Those credits supported a broad operating program: two App Store launches, a six-game ReachFi arcade, 15 daily proof-of-work scouting cycles, five external pull requests merged, and a public integration between Codex and HyperAgent.

The core HyperAgent value proposition worked: one account gave me access to specialized models that moved between research, coding, critique, and documentation.

One early Scout configuration I designed also recorded $1,149.26 in platform usage.

That was my configuration and integration failure. I found no evidence that HyperAgent operated outside its documented behavior. The incident showed that my controls had not caught up with the autonomy I was granting the system.

I reproduced the failures, repaired the spending rails, documented the remaining limitations, and published an executable proposal for a first-party gateway.

This report covers the work, the failure, the verified controls, and the product opportunity.

**Disclosure:** HyperAgent provided the platform credits used in this work. They did not review or approve this article.

## Executive Summary

- **Portfolio:** STAK and FUSE reached the App Store. ReachFi became a live game studio and free arcade. A proof-of-work Scout produced five merged public pull requests.
- **Incident:** One Scout configuration I designed recorded $1,149.26 in platform usage. A persisted configuration and a cross-process race exposed two material gaps in my local controls.
- **Build:** The public HyperAgent Codex Bridge now includes atomic budgets, fail-closed locks, durable idempotency, hard timeouts, structured logs, health probes, an OpenAPI 3.1 contract, an SSE specification, and black-box conformance tests.
- **Verification:** The clean local run passed 75 tests with zero failures. Three environment-dependent tests were skipped. CI covers Linux, macOS, and Windows on Node 20 and 22.
- **Proposal:** The bridge defines one possible path for a first-party Responses-compatible gateway with native streaming, authoritative cost data, platform-enforced budgets, provider-backed idempotency, and native cancellation.

## The Integration

I wanted HyperAgent's model selection and prepaid credits inside the workflow where I already build: Codex reading local repositories, applying patches, running tests, and keeping consequential actions behind local policy.

The bridge separated reasoning from execution.

```text
Codex CLI or Codex App
        |
        | Responses-compatible request
        v
local loopback bridge
        |
        | OAuth-authenticated MCP
        v
named HyperAgent relay agent
        |
        v
selected model + HyperAgent credits
```

The live proof worked. Codex sent a reasoning request to a named HyperAgent agent. The agent selected a local shell tool. Codex executed that tool on my Mac under its own controls. The tool result returned to HyperAgent, and the final response returned to Codex.

HyperAgent recorded the usage. The Codex subscription meter did not move.

The route was functional. The economics and control boundaries needed more work.

## The Spend Incident

My integration was forwarding more context than the task required, including developer instructions, skills, environment details, project guidance, and conversation history. A local tool loop could also trigger several paid relay requests.

Version 0.4.1 added context stripping, bounded history, a retained-input ceiling, low-effort defaults, multi-agent blocking, and a six-request daily cap.

The first audit found two material gaps in my local controls.

First, the installed Mac bridge still advertised a ten-request daily cap. The source default had changed to six, but an older persisted configuration silently won during the upgrade.

Second, the usage counter was safe inside one process. Two bridge processes could still race and spend against the same budget.

My bridge interface showed a control that the underlying system could not fully enforce. I held the article and fixed the implementation.

## Building the Control Plane

Version 0.4.2 repaired the upgrade and concurrency failures.

Old unversioned configurations now migrate to the safer default without rotating OAuth or local authentication. Explicit operator overrides remain explicit. Independent bridge processes share one atomic budget. Stale locks recover. Lock failure denies the request.

An eight-process test against a cap of three proves that exactly three requests are admitted.

Version 0.5.0 moved the project from a working adapter to an executable product proposal. It publishes:

- an OpenAPI 3.1 contract for `POST /v1/responses`;
- a normative SSE success and failure state machine;
- deterministic agent and model selection;
- local bearer authentication;
- bounded, durable idempotency and replay across restarts;
- crash-safe budget reservations;
- hard timeouts around OAuth, thread creation, polling, and response reads;
- content-free structured logs;
- liveness and readiness probes;
- black-box conformance tests;
- and an official OpenAI JavaScript client fixture.

The clean local run passed 75 tests with zero failures. Three environment-dependent tests were skipped. The project runs CI across Linux, macOS, and Windows under Node 20 and 22.

The deliverable is larger than a feature request. It gives HyperAgent a public implementation reference, test harness, security boundary, failure model, rollback path, and a working adapter that demonstrates integration feasibility.

## Current Boundaries

The public project remains a local bridge over HyperAgent's documented OAuth MCP agent-thread surface.

The adapter frames SSE after a HyperAgent thread completes. Native token streaming is unavailable through the current route.

The documented thread result does not provide authoritative token or dollar usage, so the response omits those fields.

Idempotency is durable but local and bounded. It is not provider-backed.

Disconnecting stops local polling. It does not prove that native HyperAgent work stopped.

The gateway refuses non-loopback binds. It was designed as a local integration and executable specification, not a public shadow inference service.

These boundaries are documented in the contract and covered by adversarial tests where possible.

## The Product Opportunity

The next step is a first-party HyperAgent gateway with:

- `POST /v1/responses`;
- OAuth bearer authentication;
- native SSE token streaming;
- explicit model and agent selection;
- authoritative usage and cost metadata per response;
- platform-enforced budgets;
- provider-backed idempotency;
- native cancellation and reconciliation.

Codex and other OpenAI-compatible clients could then connect through a small provider configuration. Context would remain structured. Tool calls would remain native. HyperAgent could enforce budgets and reconcile costs at the platform layer that owns the execution data.

The local adapter should eventually become unnecessary. The contract and conformance suite are designed to make that transition cheaper.
